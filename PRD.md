# PRD: Автоматический отчёт по аварийным ситуациям на сети

## 1. Общие сведения

**Продукт:** Система автоматического формирования отчётов по аварийным ситуациям на сети АО «Казахтелеком»

**Заказчик:** ДТПРС, г. Алматы

**Источник данных:** Telegram-группа «Minor ПБ (оповещ...)» с подчатами (темами) по зонам ответственности (ДЭСД)

**Поставщик данных:** бот `ecus_bot`, публикующий структурированные сообщения об аварийных ситуациях с обновлением каждый час

---

## 2. Цель продукта

Автоматизировать сбор, агрегацию и визуализацию данных об аварийных ситуациях на сети из Telegram-группы с подчатами. Обеспечить руководство ДТПРС оперативной сводкой в формате Excel с разбивкой по городам, зонам ответственности, объектам и характеру повреждений. При простое более 8 часов — автоматически направлять уведомление в отдельный Telegram-чат.

---

## 3. Источник данных

### 3.1. Структура Telegram-группы

Группа содержит подчаты (темы/топики), разделённые по зонам ответственности:

- Восточно-Казахстанский ДЭСД
- ОДС и ГЦУСТ
- Карагандинский ДЭСД
- Актюбинский ДЭСД
- РРЛ и АМС
- Атырауский ДЭСД
- ДЭСД Жетысу
- Южно-Казахстанский ДЭСД
- Павлодарский ДЭСД
- и другие

### 3.2. Формат сообщения от ecus_bot

Каждое сообщение содержит следующие поля (ключ: значение, построчно):

| Поле | Пример | Описание |
|------|--------|----------|
| Номер ПБ | 000000028034134 | Уникальный идентификатор аварии |
| Время создания ПБ | 07.07.2026 06:52:39 | Дата и время возникновения |
| Район | Уланский | Район расположения объекта |
| Город | Отрадное | Город расположения объекта |
| Узел сети | Отрадное DSLAM_E5600 | Название объекта (узла сети) |
| Группа исполнителей | ЕЦУС_Т1_Аст_СД | Ответственная группа |
| Зона ответственности | Восточно-Казахстанский ДЭСД | Зона ответственности (ДЭСД) |
| Характер повреждения ПБ | Станционное | Тип повреждения (Станционное / Линейное) |
| Подробное описание аварии | Устройство недоступно в Zabbix | Текстовое описание |
| Источник аварии | Unavailable by ICMP ping | Техническая причина |
| Фактическая длительность | 0 сут. 3 ч. 15 мин. | Накопленное время простоя |

### 3.3. Логика обновлений

Бот отправляет обновления по одному и тому же Номеру ПБ каждый час с нарастающей «Фактической длительностью». Отдельного сообщения о восстановлении связи не поступает. Итоговый простой определяется как максимальное значение длительности по данному Номеру ПБ.

## 5. Эскалация: уведомления в Telegram-чат

### 5.1. Порог срабатывания

Простой более **8 часов** (480 минут) по любой аварии.

### 5.2. Канал уведомления

Отдельный Telegram-чат (название/ID указывается в конфигурации скрипта, параметр `ALERT_CHAT`).

### 5.3. Формат сообщения

При обнаружении аварий с простоем >8 часов в чат отправляется сводка:

```
🚨 СВОДКА: ПРОСТОЙ БОЛЕЕ 8 ЧАСОВ
Всего аварий: N
━━━━━━━━━━━━━━━━━━━━━

🔴 ПРОСТОЙ БОЛЕЕ 8 ЧАСОВ
━━━━━━━━━━━━━━━━━━━━━
📍 Город: [город]
🏗 Объект: [узел сети]
⏱ Простой: [длительность]
🏢 Зона ответственности: [ДЭСД]
📋 Номер ПБ: [номер]
🕐 Начало: [дата и время]
🔧 Характер: [тип повреждения]
━━━━━━━━━━━━━━━━━━━━━
```

Аварии в сводке отсортированы по убыванию простоя. Если аварий с простоем >8ч нет, сообщение не отправляется.

## 6. Техническая архитектура

### 6.1. Компоненты

| Компонент | Файл | Назначение |
|-----------|------|------------|
| Парсер сообщений | `parser.py` | Разбор текста сообщений ecus_bot в структурированные записи |
| Генератор отчёта | `report_builder.py` | Агрегация данных, построение Excel-файла с 9 листами, диаграммами, форматированием; формирование текста алертов |
| Сборщик данных | `fetch_telegram.py` | Подключение к Telegram, обход подчатов группы, вызов парсера и генератора, отправка алертов |

### 6.2. Стек технологий

| Технология | Назначение |
|------------|------------|
| Python 3.10+ | Язык реализации |
| Telethon | Подключение к Telegram через MTProto (личный аккаунт) |
| openpyxl | Генерация Excel-файлов с форматированием и диаграммами |

### 6.3. Подключение к Telegram

Используется личный аккаунт пользователя через Telegram API (MTProto, библиотека Telethon). Требуется однократная авторизация с вводом кода подтверждения. Сессия сохраняется в файле `.session`.

Необходимые учётные данные (получаются на https://my.telegram.org):

- `API_ID` — числовой идентификатор приложения
- `API_HASH` — хеш приложения

### 6.4. Логика дедупликации

По одной аварии (Номер ПБ) может поступать множество сообщений с обновлённой длительностью. В отчёт попадает только запись с максимальной «Фактической длительностью» — это итоговый простой на момент формирования отчёта.

## 7. Конфигурация

Все параметры задаются в блоке `CONFIG` файла `fetch_telegram.py`:

| Параметр | Описание | Значение по умолчанию |
|----------|----------|-----------------------|
| `API_ID` | Telegram API ID | — (обязательно) |
| `API_HASH` | Telegram API Hash | — (обязательно) |
| `SESSION_NAME` | Имя файла сессии | `dtprs_session` |
| `SOURCE_GROUP` | Группа-источник данных | `Minor ПБ (оповещ...)` |
| `ALERT_CHAT` | Чат для уведомлений о простое >8ч | — (обязательно) |
| `BOT_SENDER` | Username бота-источника | `ecus_bot` |
| `DAYS_BACK` | Период выгрузки (дней назад) | `7` |
| `DATE_FROM` | Фиксированная дата начала периода | `None` |
| `DATE_TO` | Фиксированная дата конца периода | `None` |
| `OUTPUT_PATH` | Путь к выходному файлу | `avariynyy_otchet.xlsx` |

Порог простоя для эскалации задаётся в `report_builder.py`:

| Параметр | Описание | Значение по умолчанию |
|----------|----------|-----------------------|
| `CRITICAL_THRESHOLD_MINUTES` | Порог простоя в минутах | `480` (8 часов) |

## 8. Режимы запуска

### 8.1. Ручной запуск

```bash
python fetch_telegram.py
```

### 8.2. По расписанию (Windows)

Планировщик заданий → Создать задачу → Триггер (например, каждый день в 08:00) → Действие: запуск `python.exe` с аргументом `fetch_telegram.py`.

### 8.3. По расписанию (Linux/сервер)

```bash
crontab -e
# Каждый день в 08:00:
0 8 * * * cd /путь/к/скрипту && /usr/bin/python3 fetch_telegram.py
```

## 9. Безопасность

| Аспект | Описание |
|--------|----------|
| Файл сессии | `.session` — эквивалент ключа доступа к Telegram-аккаунту. Хранить локально, не передавать третьим лицам |
| API-ключи | `API_ID` и `API_HASH` не коммитить в публичные репозитории |
| Данные | Отчёт содержит служебную информацию об инфраструктуре сети. Соблюдать политику информационной безопасности АО «Казахтелеком» |
